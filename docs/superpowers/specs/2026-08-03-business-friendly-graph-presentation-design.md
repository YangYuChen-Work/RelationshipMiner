# 面向非技术用户的业务关系图展示设计

## 背景

当前界面仍大量使用 `class_name`、数据库表名、字段名、实体 ID、模型 ID、任务 ID、置信度等技术信息。它们可以帮助开发者追踪分析过程，但不能帮助非技术用户直接理解“有哪些业务对象”以及“这些对象为什么有关联”。

本次改造覆盖完整使用流程，但以分析结果页的节点名称为最高优先级：选择页做必要的业务化简化，图谱和详情页建立一致的业务展示语言。视觉方向参考用户提供的知识图谱截图，采用浅色业务视图、实心彩色节点、节点下方业务名称和简短关系动词。

## 核心原则

`name` 表示用户可理解的业务对象，`class_name` 提供对象类型及关系判断的主要上下文。其他字段仅用于辅助判断两个 `name` 是否存在关联，不得取代 `name` 成为节点名称、关系主体或主要对象类型。

由此产生以下不可偏离的约束：

- 每个图谱节点代表一条以 `name` 命名的业务对象。
- 每条关系表达为“业务名称 A 与业务名称 B 的关系”。
- `name + class_name` 是关系分析的主要判断输入。
- 其他字段只用于补充证明、提高置信度或识别具体关系。
- 业务编号仅用于区分重名节点，不改变节点的业务含义。
- `class_name`、数据库 ID、字段名、表名、模型 ID和任务 ID不得占据节点或普通详情的主要位置。
- 辅助字段即使值显著，也不能被选为节点标题或关系主体。

## 目标与非目标

### 目标

- 所有正常节点以 `name` 为主标题。
- 只有重名节点在第二行显示业务编号。
- `class_name` 自动参与内部关系判断，但不出现在节点或普通详情中。
- 关系线使用“包含”“装配于”“用于检验”等简短业务动词。
- 选择页同时呈现推测出的表语义名称和原始表名。
- 默认详情聚焦业务结论，原始字段和技术依据按需展开。
- 搜索、键盘访问、画布、详情和关系列表使用同一套名称。
- 保持现有分析、导出、布局、筛选和错误恢复能力。

### 非目标

- 不重写现有关系发现算法。
- 不改变 `name + class_name` 为主要关系判断上下文的规则。
- 不删除导出快照中的可追溯技术信息。
- 不增加图谱编辑、人工创建关系或数据回写能力。
- 不引入新的图可视化框架或替换现有 Canvas/Web Worker 布局。

## 方案选择

采用“前后端协作的业务展示层”。

未采用纯前端修饰，因为前端只能从当前返回字段猜测名称和编号，规则容易分散到画布、搜索和详情组件中，界面与导出结果也可能不一致。

未采用后端完全生成最终界面文案，因为这会把换行、查重范围和视觉降级等前端呈现策略固化在服务端，降低后续调整界面的灵活性。

协作方案中，后端负责稳定的业务语义，前端负责上下文相关的呈现：

- 后端识别并读取 `name`、`class_name` 和候选业务编号。
- 后端输出稳定的业务名称、业务编号候选、关系业务文案和可追溯原始信息。
- 前端负责全图查重、第二行编号、语义缩放、折叠层级和一致的可访问名称。

## 数据与关系分析规则

### 必要字段

每张参与分析的表必须具有可识别的 `name` 和 `class_name` 字段。字段名匹配应沿用现有大小写与命名约定的标准化方式，并对项目当前支持的 `class_name`、`className` 和 `class` 保持兼容。

- `name` 自动加入读取范围，并作为节点业务名称来源。
- `class_name` 自动加入读取范围，并作为关系判断的主要类型上下文。
- 用户不需要手动选择或取消这两个字段。
- 其他用户选择字段作为关系判断的辅助维度。

提交给分析器的逻辑范围必须明确区分主要上下文与辅助维度，避免把字段选择顺序解释成展示优先级。

### 节点展示元数据

后端为每个节点提供：

- `display_name`：严格来源于 `name` 的业务名称。
- `display_code`：根据业务编号候选规则得到的可选编号。
- 现有 `class_name` 与原始维度继续保留用于分析、导出和技术追踪，但不进入普通节点展示。

`display_name` 不得回退到 `class_name`、表名、数据库主键或实体 ID。`name` 为空时使用固定文案“未命名对象”，并在分析结果中产生数据质量提示。

### 业务编号推断

候选编号字段按标准化字段名匹配，优先考虑包含完整词元 `code`、`number`、`no`、`serial`、`model` 的业务字段。主键仅在它本身符合业务编号语义时才可成为候选，不能把内部自增 ID 直接作为展示编号。

候选排序必须确定性，不能依赖数据库返回列顺序。无可用编号时，前端依据稳定的实体 ID 排序生成“同名 1”“同名 2”等仅用于展示的区分文本。

### 重名范围

前端对当前图谱全部可见业务节点的标准化 `display_name` 统一查重，而不是只在单张表内查重。这样即使两个来源表包含同名对象，用户也能在当前视图中区分它们。

- 名称唯一：只显示主行 `display_name`。
- 名称重复且存在 `display_code`：第二行显示业务编号。
- 名称重复且缺少编号：第二行显示稳定的“同名 N”。

过滤关系或隐藏孤立节点不得改变“同名 N”的分配，避免同一会话中标签跳变。编号应基于完整分析快照计算。

### 关系判断原则

分析器形成候选关系或请求模型判断时，应把 `name` 和 `class_name` 作为两个对象的主要上下文。其他字段作为辅助证据输入，用于回答“这两个已命名业务对象是否有关联、是什么关系以及依据是什么”。

关系输出的主体始终是两个业务对象，辅助字段只能出现在证据中。不得因为某个辅助字段值相同，就把字段值本身提升为节点或关系主体。

## 表语义摘要

选择页需要为每张数据库表生成可读的业务语义名称。摘要器综合：

- 原始表名。
- `class_name` 的类型含义。
- 少量非空 `name` 示例。
- 字段结构，仅作为辅助上下文。

输出包括：

- 简短的中文业务类别名称，例如“装配工艺数据”。
- 原始表名。
- 记录数量。
- 最多三个经过长度限制和敏感值过滤的 `name` 示例。

语义推测不阻塞数据库表列表的首屏加载。原始表信息先展示，推测结果完成后原位更新并缓存到本次会话。推测失败时保留原始表名、数量和名称示例，不影响选择与分析。

## 前端信息架构

### 选择页

页面标题改为“选择要分析的业务数据”，主按钮改为“生成业务关系图”。

每张表使用业务数据集卡片：

- 主标题：推测出的表语义名称。
- 次级来源：原始表名。
- 摘要：记录数量和若干 `name` 示例。
- 展开说明：“系统将使用名称和对象类型判断关系。”
- 固定上下文：`name` 与 `class_name` 自动参与，不提供取消操作。
- 可选区域：其余字段归类为“辅助判断依据”。
- 技术区域：数据库类型、主键、外键等默认折叠。

若需要在界面中提及 `name`，使用“节点名称”；若需要说明 `class_name`，只使用“对象类型由系统自动识别”，不要求非技术用户理解 Java 类名。

### 图谱工作台

工作台采用浅色业务视图：

- 浅灰画布、白色详情面板、低对比关系线。
- 节点为带白色细描边的实心彩色圆。
- 节点颜色表达业务对象类型或来源分组，颜色图例使用业务语义名称。
- 节点下方主行显示业务名称。
- 仅重名节点显示第二行业务编号或“同名 N”。
- 节点大小继续表达关系度数，但设置清晰的最小和最大范围。
- 悬停或选中节点时保留现有一跳聚焦机制。
- 技术 ID、表名和类名不作为视觉缩放回退内容。

概览、工作和细节缩放级别可以控制标签密度，但被选中或悬停的节点始终显示业务名称；重名区分文本与主名称保持绑定，不能单独出现。

### 关系线

默认关系标签使用简短业务动词，如“包含”“装配于”“用于检验”。后端优先提供业务关系文案，前端进行长度和空值处理。

无法生成可读业务文案时显示“相关”，原始关系类型只放在技术依据中。普通视图不显示模型生成的内部类别名、空关系类型或字段匹配方法名。

### 节点与关系详情

节点详情默认显示：

- 业务名称。
- 必要时显示业务编号。
- 直接关联的业务对象，使用对方业务名称。
- 每条关系的简短业务动词和通俗解释。

关系详情默认显示：

- “业务名称 A → 业务名称 B”。
- 业务关系动词。
- 通俗解释。
- “判断依据”：仅列真正支持该关系的辅助字段和值，并使用业务化说明。
- 将数值置信度转为“明确”“较可信”“可能有关”等级。

“技术依据”默认折叠，可包含 `class_name`、原始关系类型、匹配方法、精确置信度、模型 ID和任务 ID。“查看原始数据”默认折叠，保留节点全部原始字段。两个折叠区服务于排查和专业用户，不参与普通浏览的视觉层级。

### 工具栏与状态文案

工具栏优先展示“对象数量”和“业务关系数量”，不再强调“表节点、实体边、表边”等内部图模型术语。高级筛选仍可保留置信度能力，但默认文案使用关系可信程度；精确阈值属于高级设置。

空状态、部分结果和失败状态必须用业务影响描述结果，例如“部分对象的关系尚未判断完成”，并将候选数量、模型失败等诊断信息放入可展开技术详情。

## 组件与模块边界

### 后端

- 表语义摘要器：从表元数据与安全样本生成业务类别摘要，失败可独立降级。
- 节点展示信息生成器：从 `name` 和候选编号字段生成稳定元数据。
- 关系分析输入构造器：明确组织主要上下文 `name + class_name` 与辅助证据字段。
- 关系业务文案规范化器：保留原始类型，同时生成简短可读动词。

每个模块通过明确数据结构沟通，表摘要失败不得影响节点构建，展示信息失败不得丢弃分析记录，业务文案降级不得删除原始关系。

### 前端

- 业务数据集卡片：替代以数据库结构为主的表折叠项。
- 实体展示模块：统一计算查重结果、主副标签、搜索文本和可访问名称。
- 图谱主题模块：集中管理浅色画布、实心节点、业务颜色和聚焦样式。
- 业务详情面板：负责普通信息、判断依据、技术依据和原始数据的分层。
- 业务文案适配器：统一工具栏、进度、空状态和错误状态术语。

画布绘制、搜索、键盘命中和详情面板必须消费同一个实体展示结果，不能各自重新猜测名称。

## 数据流

1. 选择页请求表列表并立即展示原始表名。
2. 后端读取表结构、记录数量以及受限的 `name`/`class_name` 样本，异步返回或补充表语义摘要。
3. 用户选择业务数据集和可选辅助字段；`name` 与 `class_name` 由系统自动加入分析范围。
4. 后端构建以 `name + class_name` 为主要上下文、其他字段为辅助证据的分析输入。
5. 图谱构建阶段生成 `display_name`、`display_code`、业务关系文案与完整可追溯数据。
6. 前端基于完整快照生成稳定的全图重名索引和共享展示模型。
7. 画布、搜索、详情、键盘访问和导出视图消费一致的业务展示信息。

## 异常与降级

- 缺少 `name`：该表不能开始分析，提示“缺少业务名称字段”。
- 缺少 `class_name`：该表不能开始分析，提示“缺少对象类型信息，无法进行主要关系判断”。
- `name` 为空：保留节点，显示“未命名对象”，并产生数据质量提示。
- 表语义推测失败：显示原始表名、数量和名称示例，不阻塞分析。
- 业务编号识别失败：重名节点使用稳定的“同名 N”。
- 关系业务文案失败：显示“相关”，原始关系仍可在技术依据中追踪。
- 技术折叠区单个值无法序列化：显示安全占位文本，不使详情面板崩溃。
- 布局或 Canvas 失败：沿用现有错误边界、重试、导出和新分析能力。

任何降级都不得把 `class_name`、表名或数据库 ID重新提升为节点主标题。

## 测试与验收

### 后端单元测试

- `name` 与 `class_name` 自动加入读取与分析上下文。
- `name` 严格生成 `display_name`，不回退到辅助字段或技术标识。
- 业务编号候选按语义和确定性顺序选择。
- 内部自增主键不会被误当成业务编号。
- 关系判断输入清晰区分主要上下文与辅助证据。
- 表语义摘要成功、超时和失败降级均不阻塞表选择。
- 关系业务文案无法生成时稳定回退到“相关”。

### 前端单元测试

- 唯一名称只生成单行标签。
- 全图重名生成第二行业务编号。
- 重名且无编号时生成稳定“同名 N”。
- 过滤关系和隐藏孤立节点不改变重名编号。
- `class_name`、表名、实体 ID和辅助字段永不成为节点标题回退。
- 搜索、辅助朗读和详情使用共享展示名称。
- 技术依据和原始数据默认折叠。

### 组件与集成测试

- 数据集卡片同时显示语义表名与原始表名。
- `name` 和 `class_name` 自动参与，用户只能选择辅助判断字段。
- 图谱使用浅色画布和实心彩色节点。
- 关系线显示业务动词，选中后显示通俗解释和必要证据。
- 工具栏、进度、空状态和错误状态不暴露内部图模型术语。
- 缺少必要字段时不能提交分析，并给出明确业务提示。
- 旧快照缺少 `display_code` 或业务文案时可以安全降级展示。

### 视觉验收

使用真实或具代表性的 20 节点与 200 节点图，在 1920×1080、1366×768 和窄屏视口验证：

- 正常节点只显示 `name`。
- 重名节点才显示第二行编号。
- 节点是清晰的实心彩色圆，名称位于节点下方。
- 画布为浅色业务视图，关系线不压过节点名称。
- `class_name`、数据库 ID和表名不出现在普通节点与详情中。
- 关系标签是简短业务动词。
- 选择页能凭语义表名、原始表名和名称示例辨认数据集。
- 200 节点下仍可通过缩放、聚焦和搜索识别目标对象。

## 兼容与迁移

公开图谱协议新增的展示字段应保持可选，以便旧 JSON 快照继续导入。前端遇到旧快照时，依次使用 `dimensions.name`、有效且非状态值的现有 `display_name`、固定文案“未命名对象”；不得从 `class_name`、表名或实体 ID生成主标题。缺少业务编号的重名项使用“同名 N”。

导出快照继续保留完整技术数据，同时包含后端生成的业务展示元数据，使同一快照再次打开时名称和关系文案保持一致。

## 成功标准

一名不了解 Java 类名和数据库结构的用户，在不展开任何技术区域的情况下，应能够：

1. 根据语义表名、原始表名和名称示例选出要分析的业务数据。
2. 在图谱中直接读出每个节点代表的业务对象。
3. 区分重名对象。
4. 从关系动词和通俗解释理解两个业务对象为何有关联。
5. 在需要时查看辅助判断依据，而不被内部实现信息干扰。
