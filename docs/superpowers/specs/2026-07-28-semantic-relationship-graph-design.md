# 语义关系图谱重构设计

日期：2026-07-28
状态：已完成讨论，待用户审阅

## 1. 背景

当前系统希望从用户选择的数据库表和字段中发现关系并生成图谱，但已有实现存在以下根本问题：

- 数据层关系依赖 AI 返回字段对；AI 失败时只剩物理外键。
- AI 返回非法或截断 JSON 时被静默转换为空决策，最终表现为“分析成功但零关系”。
- AI 分析整张表的全部字段，而关系计算只读取用户选择字段，可能推荐无法执行的字段对。
- AI 返回的编辑距离、数值差异等算法没有真正执行。
- 外键计算错误地使用目标表主键，而不是外键声明中的目标字段。
- `class_name` 被前端强制选择，但当前只用于节点展示，没有参与关系推理。
- 7000 个实体会产生数万个 SVG 元素；一旦存在边，全局力导向布局还会进一步阻塞浏览器。

本设计重构关系图谱的领域模型和分析流程，使系统能够在三分钟目标内，从用户选择的表、字段和字段值中生成可解释的表关系与实体关系。

## 2. 已确认的产品决策

### 2.1 关系分层

系统同时支持：

- **强关系**：数据库外键、唯一标识匹配等可验证关系。
- **弱关系**：由大模型根据表名、字段名和具体字段值推理出的语义关系。

强弱关系都直接进入图谱，不要求用户预先确认。前端使用样式、置信度和筛选器区分关系。

### 2.2 图谱节点

图中只存在两类节点：

- 表节点（Table Node）
- 实体节点（Entity Node），对应数据库中的一条记录

字段不作为节点。字段名和字段值只是关系推理维度，以及关系边的证据。

图中只显示：

- 表节点与表节点之间的关系
- 实体节点与实体节点之间的关系

实体通过属性归属来源表，前端使用视觉分组表达这种归属，不绘制“表到实体”的边。

### 2.3 用户选择范围

用户在前端选择：

- 参与分析的表
- 每张表中参与语义推理的字段

只有用户选择的字段能够进入实体语料、候选检索、大模型提示和边证据。

系统可以额外读取：

- 主键：仅用于生成稳定实体 ID。
- `class_name`：仅作为可选展示信息。
- 物理外键字段：仅用于执行数据库已声明的确定关系。

这些系统字段不计入用户选择的语义推理维度。

### 2.4 大模型角色

大模型承担两项职责：

1. 根据表名、字段名、字段类型和少量样本生成跨表关系计划。
2. 根据表上下文、字段上下文和具体实体值判断候选实体是否存在业务关系。

除物理外键和明确唯一标识关系外，最终是否建立关系由大模型决定。

### 2.5 性能目标

- 约 7000 条实体记录。
- 最多 10 张表。
- 单次分析目标在 3 分钟内完成。
- 允许将用户选择字段的原始值发送给外部大模型。
- 第一版不实现本地综合关系评分。

## 3. 方案选择

### 3.1 不采用全量实体组合

7000 条记录的无向实体组合约为 2450 万对。逐对调用大模型无法满足成本和三分钟目标。

系统不生成全量笛卡尔积，而是把所有实体构造成可检索语料，通过关系计划、结构化索引和向量索引召回少量候选，再交给大模型判断。

### 3.2 不采用自由协作式多 Agent

第一版不使用多个自主 Agent 分别分析数据库，原因是：

- 多个 Agent 会重复读取 Schema 和样本。
- 不同 Agent 的关系类型和置信度标准可能不一致。
- 需要额外解决重复边、冲突结论和结果合并。
- 多 Agent 本身不能解决候选搜索问题。

系统采用一个深层的关系分析模块，内部包含关系规划、候选检索、语义判断和图谱组装职责。不同表对可以由受控任务并行执行，但共享同一套关系模型和评分标准。

## 4. 核心模块

核心模块名称为 `RelationshipAnalyzer`。

它的外部接口应保持小而稳定：

```text
analyze(AnalysisScope) -> AnalysisResult
```

调用者只需要理解：

- 用户选择的数据范围
- 分析状态和错误模式
- 返回的表关系、实体关系、证据和诊断统计
- 三分钟性能目标

数据库访问、索引实现、大模型供应商、批处理和并发策略隐藏在模块实现内部。

### 4.1 内部职责

`RelationshipAnalyzer` 内部包含以下职责：

1. **范围构建**：验证表和字段选择，区分推理字段与系统字段。
2. **实体语料构建**：把记录转换为结构化实体文档。
3. **关系规划**：调用大模型生成允许分析的表对、字段角色和关系类型。
4. **候选检索**：使用结构化索引和向量索引检索相关实体。
5. **确定关系执行**：执行物理外键和明确唯一标识关系。
6. **语义判断**：批量调用大模型判断所有非确定性候选。
7. **关系合并**：合并重复候选、多重关系和多组证据。
8. **表关系聚合**：根据实体关系生成表关系。
9. **结果组装**：返回图谱、完整性状态、警告和诊断统计。

数据库、向量检索和大模型分别通过可替换适配器接入。生产适配器和测试适配器必须满足相同接口。

## 5. 数据模型

### 5.1 分析范围

```json
{
  "tables": [
    {
      "name": "process",
      "dimensions": ["name", "description", "creator"]
    },
    {
      "name": "part",
      "dimensions": ["name", "model"]
    }
  ],
  "time_budget_seconds": 180
}
```

`dimensions` 是用户选择的语义推理字段。主键、外键和 `class_name` 不应被混入该集合。

### 5.2 实体文档

```json
{
  "entity_id": "process:18",
  "table_name": "process",
  "display_name": "涡轴发动机燃气发生器转子装配工艺（样）",
  "class_name": "RotorAssemblyProcess",
  "dimensions": {
    "name": "涡轴发动机燃气发生器转子装配工艺（样）",
    "description": "燃气发生器转子装配……",
    "creator": "张三"
  },
  "normalized_dimensions": {
    "name": "涡轴发动机燃气发生器转子装配工艺样",
    "description": "燃气发生器转子装配",
    "creator": "张三"
  },
  "search_text": "表：工艺管理；工艺名称：涡轴发动机燃气发生器转子装配工艺（样）；创建人：张三"
}
```

规范化值用于检索和去重，原始值用于展示和证据。

### 5.3 关系计划

```json
{
  "source_table": "process",
  "target_table": "part",
  "relation_type": "工艺涉及零件",
  "direction": "source_to_target",
  "source_dimensions": ["name", "description"],
  "target_dimensions": ["name", "model"],
  "retrieval_modes": ["keyword", "semantic"],
  "candidate_limit_per_source": 20,
  "reason": "工艺名称或描述可能包含被加工、装配的零件名称或型号"
}
```

关系计划限制候选检索范围。没有进入关系计划的表对不进行实体级语义检索。

### 5.4 实体节点

```json
{
  "id": "process:18",
  "table_id": "process",
  "display_name": "涡轴发动机燃气发生器转子装配工艺（样）",
  "class_name": "RotorAssemblyProcess",
  "dimensions": {
    "name": "涡轴发动机燃气发生器转子装配工艺（样）",
    "creator": "张三"
  }
}
```

显示名称按以下顺序选择：

1. 名称、标题、编号等可识别的用户选择字段。
2. 第一个非空的用户选择字段。
3. 主键值。

存在 `class_name` 时，节点来源标签显示为 `表名 · 短类名`；不存在时只显示表名。

### 5.5 实体关系

```json
{
  "source": "process:18",
  "target": "part:361",
  "relations": [
    {
      "type": "工艺涉及零件",
      "direction": "source_to_target",
      "strength": "weak",
      "confidence": 0.91,
      "explanation": "该装配工艺描述的对象是燃气发生器转子",
      "evidence": [
        {
          "source_field": "工艺名称",
          "source_value": "燃气发生器转子装配工艺",
          "target_field": "零件名称",
          "target_value": "燃气发生器转子",
          "method": "llm_semantic_reasoning",
          "reason": "工艺名称明确包含并指向该零件"
        }
      ]
    }
  ]
}
```

同一对实体存在多种关系时合并为一条图边，但必须保留独立的关系类型、方向、置信度、解释和证据，不能只拼接标签字符串。

### 5.6 表关系

```json
{
  "source_table": "process",
  "target_table": "part",
  "relation_types": ["工艺涉及零件"],
  "strong_count": 12,
  "weak_count": 274,
  "entity_edge_count": 286,
  "average_confidence": 0.84,
  "supporting_entity_edges": ["edge:1", "edge:2"]
}
```

满足以下任一条件时生成表关系：

- 至少存在一条强实体关系。
- 至少存在三条同类型弱实体关系。
- Schema 层已经确认两表存在关系。

## 6. 分析流水线

### 阶段 1：读取与验证

- 校验选择的表和字段真实存在。
- 读取所有选中记录的用户维度字段。
- 自动补充主键、必要外键和可选 `class_name`。
- 未选择字段不得进入模型提示、检索文本或关系证据。

### 阶段 2：构建实体语料

- 将每条记录转换为 `EntityDocument`。
- 对姓名、编号、型号、日期和空白进行基础规范化。
- 保留原始值。
- 对完全相同的规范化实体签名去重，避免重复推理；推理结果再应用到所有对应记录。

### 阶段 3：生成关系计划

大模型接收：

- 用户选择的表名
- 用户选择的字段名和类型
- 每张表少量样本

大模型输出受结构化 Schema 约束的 `RelationshipPlan` 列表。计划说明哪些表可能相关、字段承担什么语义角色、关系方向、关系类型和候选检索方式。

大模型不在此阶段枚举实体关系。

### 阶段 4：构建索引并召回候选

建立两类索引：

- 结构化倒排索引：人员、编号、型号、日期和关键词。
- 语义向量索引：名称、描述、备注等文本。

对每个关系计划，只从目标表中检索 Top-K 候选。向量相似度仅用于候选检索排序，不作为最终关系分数，也不能自动创建弱关系。

### 阶段 5：执行确定关系

以下关系无需大模型再次判断：

- 物理外键关系，必须使用外键声明中的源字段和目标字段。
- 明确唯一标识关系，例如经过类型和唯一性验证的同一业务 ID。

这些关系标记为强关系，并记录确定性来源。

### 阶段 6：大模型判断非确定性候选

所有非确定性候选由大模型最终判断。

调用方式：

- 一个源实体及其多个目标候选放入同一次请求。
- 多个请求使用有限并发。
- 输出必须符合固定 JSON Schema。
- 输出包含是否相关、关系类型、方向、置信度、解释和引用字段。
- 一个工艺可以在一次判断中关联多个零件。

第一版不实现本地综合关系评分，也不以本地相似度自动建立弱关系。

### 阶段 7：合并与聚合

- 对称候选去重。
- 合并同一实体对的多重关系。
- 保留所有独立证据。
- 从实体关系聚合表关系。
- 计算强弱关系数量、支持实体数和平均置信度。

### 阶段 8：输出结果

输出内容包括：

- 表节点
- 实体节点
- 表关系
- 实体关系
- 模型与分析配置
- 完整性状态
- 警告
- 各阶段诊断统计

## 7. 时间预算

7000 实体的目标预算：

- 数据读取、规范化和建索引：20–30 秒。
- 生成关系计划：10–20 秒。
- 候选检索：20–40 秒。
- 大模型批量语义判断：60–90 秒。
- 合并、聚合、序列化和传输：约 20 秒。

时间预算是任务级约束，不是只在阶段之间检查。每个数据库读取、检索批次和模型调用都必须检查剩余时间。

达到预算时：

- 保留已经完成的确定关系和语义关系。
- 停止启动新的模型请求。
- 返回 `partial` 状态。
- 报告未处理候选数量。

不能将未完成分析表示为“完整分析但零关系”。

## 8. 分析状态与错误处理

任务状态：

- `complete`：全部候选推理完成。
- `partial`：已有可信图谱，但部分候选因超时、限流、预算或模型错误未完成。
- `failed`：无法形成可信结果。

进度事件必须包含真实统计：

```json
{
  "phase": "semantic_judging",
  "message": "正在进行实体语义推理",
  "entities_read": 7126,
  "plans_created": 4,
  "candidates_retrieved": 8420,
  "candidates_completed": 6800,
  "entity_edges_created": 1286
}
```

模型输出解析失败时：

1. 记录任务阶段和非敏感响应摘要。
2. 使用结构化修复提示重试一次。
3. 再次失败则将受影响批次标记为未完成。
4. 根据其余批次结果返回 `partial` 或 `failed`。
5. 前端明确展示未完成范围。

空关系结果只有在所有计划和候选均完成判断后，才能表示“确实未发现关系”。

## 9. 图谱展示

### 9.1 统一图与表分组

前端使用一张统一图：

- 表节点位于各表实体分组的中心或标题区域。
- 表节点之间绘制聚合表关系。
- 实体节点在来源表的分组区域内布局。
- 实体节点之间绘制语义关系。
- 不绘制表到实体的归属边。

### 9.2 语义缩放

- 远景显示表节点、表关系和实体密度。
- 放大后显示实体节点和实体关系。
- 进一步放大后显示实体文字、边标签和证据入口。
- 搜索和点击可以直接定位任意实体。
- 点击表关系突出所有支撑该表关系的实体关系。

所有实体保留在图谱结果中，但前端只绘制当前缩放级别和可视区域所需细节。

### 9.3 渲染技术

- 实体和边使用 Canvas 或 WebGL。
- 不再为每个实体创建多个 SVG 元素。
- 表级布局最多处理 10 个表节点。
- 实体只在所属表分组内布局。
- 不运行全局 7000 节点力导向布局。
- 布局计算放入 Web Worker。
- 实体标签只在足够缩放级别显示。

### 9.4 关系详情

点击实体关系后显示：

- 关系类型和方向
- 强弱属性
- 大模型置信度
- 源字段、源值、目标字段和目标值
- 中文推理解释
- 模型标识和分析任务标识

弱关系分析后直接显示。置信度滑块只控制可见性，不删除结果。

## 10. 测试设计

`RelationshipAnalyzer` 的外部接口同时作为调用接缝和端到端测试接缝：

```text
AnalysisScope
→ AnalysisResult(table_edges, entity_edges, evidence, status, diagnostics)
```

测试使用数据库、向量索引和大模型适配器，但必须通过生产模块的同一接口运行。

### 10.1 核心业务用例

- `需求.创建人` 与 `操作记录.操作人` 表示同一人员时，生成“人员行为”关系。
- 同名但不同人员时，不产生错误关系。
- 工艺名称或描述指向多个零件时，一个工艺能够关联多个零件。
- 文本相似但业务语义不同的实体不建立关系。
- 多个证据支持同一实体关系时正确合并。
- 实体关系达到支持门槛后生成对应表关系。

### 10.2 范围与展示用例

- 未选择字段不能进入提示、检索文本或边证据。
- 主键自动用于实体 ID，但不成为语义维度。
- `class_name` 未选择或不存在时分析仍能完成。
- 存在 `class_name` 时节点可显示 `表名 · 短类名`。
- 字段不会作为图节点返回。

### 10.3 错误与完整性用例

- 模型返回截断 JSON 时不会返回“零关系成功”。
- 单个模型批次失败时保留其他批次并返回 `partial`。
- 模型全部失败且没有可信确定关系时返回 `failed`。
- 达到时间预算后停止新请求并报告未处理候选数。
- 只有完整判断后才能返回可信的零关系结果。

### 10.4 正确性与性能用例

- 外键引用非主键唯一字段时仍能正确建立关系。
- 相同候选不会重复调用模型。
- 7000 实体不生成全量笛卡尔积。
- 7000 实体在三分钟内完成，或在预算到达时返回明确 `partial`。
- 加载 7000 实体结果时浏览器主线程不发生长时间阻塞。
- 点击表关系能够定位其全部支撑实体关系。

## 11. 非目标

第一版不包含：

- 自由协作式多 Agent。
- 本地综合关系评分。
- 使用向量分数直接判定最终弱关系。
- 字段节点及字段到实体的图边。
- 人工确认弱关系后才进入图谱的审批流程。
- 自动修改源数据库或向数据库写回关系。
- 对未选择字段进行隐藏分析。

## 12. 成功标准

满足以下条件时视为设计目标达成：

1. 用户选择表和字段后，系统只使用这些字段值进行实体语义分析。
2. 系统能发现人员行为、工艺涉及零件等无法仅靠物理外键表达的业务关系。
3. 每条弱关系都包含字段级证据和大模型解释。
4. 表关系可以追溯到支撑它的实体关系。
5. 7000 实体不会触发全量实体组合或浏览器大规模 SVG 卡顿。
6. 模型失败、超时和未完成分析具有明确状态，不会伪装成零关系成功。
7. `class_name` 不再是必选分析字段，只作为可选展示信息。
