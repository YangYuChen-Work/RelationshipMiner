# 数据库表搜索设计

## 目标

在前端“选择数据表”区域增加表名搜索，让用户可以在约 3000 张表中通过关键词快速定位目标表。

## 范围

- 仅按表名匹配，不搜索字段名。
- 匹配忽略大小写。
- 输入时实时刷新结果，不需要提交按钮。
- 搜索只改变可见列表，不改变已选表及其字段状态。
- 不修改现有后端接口。

## 方案

搜索状态由 `TableSelector` 组件本地维护。组件对已经由 `/api/tables` 加载到 Zustand store 的完整表列表进行客户端过滤。

采用本地状态而不是全局状态，因为搜索词只服务于当前表选择界面，不需要跨组件共享或持久化。采用客户端过滤而不是新增后端接口，因为当前系统已经一次性加载完整表列表，约 3000 个短字符串的匹配成本较低。

## 交互

1. 在表列表上方显示搜索输入框，占位文本为“搜索表名”。
2. 用户输入时，列表按照表名是否包含关键词实时过滤。
3. 匹配前对搜索词去除首尾空格，并将搜索词和表名统一转为小写。
4. 清空输入框后恢复完整列表。
5. 如果数据库没有任何表，继续显示现有空状态。
6. 如果数据库存在表但搜索没有结果，显示“未找到匹配的数据表”。
7. 被搜索暂时隐藏的已选表继续计入选择数量，并保持已选字段；重新匹配后恢复其选中显示。

## 性能

- 使用 `useDeferredValue` 将列表过滤和重渲染作为低优先级更新，保证输入框在约 3000 张表时仍能即时响应。
- 使用 `useMemo` 缓存过滤结果，只在表列表或延迟后的搜索词变化时重新计算。
- 不增加固定时间的防抖，避免输入后产生人为等待。
- 本次不引入虚拟列表依赖。若实测完整渲染约 3000 行仍无法满足性能要求，再单独增加列表虚拟化。

## 组件与数据流

`TableSelector` 新增本地 `searchQuery` 状态：

1. 输入框更新 `searchQuery`。
2. `useDeferredValue(searchQuery)` 产生用于过滤的延迟值。
3. `useMemo` 根据延迟值和 store 中的 `tables` 计算 `filteredTables`。
4. 列表渲染由 `tables.map` 改为 `filteredTables.map`。
5. 表的选择与取消选择仍调用现有 `toggleTable`，不改变 Zustand store 接口。

## 错误处理

数据加载错误、重试按钮和加载状态保持现状。搜索输入框只在表列表成功加载后出现，不新增网络错误分支。

## 测试

在 `TableSelector` 组件测试中覆盖：

- 输入关键词后只显示包含关键词的表。
- 匹配忽略大小写。
- 输入关键词首尾空格不影响匹配。
- 清空搜索词恢复完整列表。
- 无匹配结果时显示专用空状态。
- 搜索隐藏已选表时选择数量与选择状态保持不变。

测试遵循先失败、再实现、最后重构的顺序。
